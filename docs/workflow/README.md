# Skill 研发流程

仓库围绕“研究 → 实验 → 规则 → 候选 → 评测 → 审查 → 发布”组织源码和工具。目录、装配入口与检查器已经落地；研究和工程 Skill 仍为开发候选，真实载具 profile 与跨任务验证需要继续积累。

研发的基本单元是一条有适用范围、证据和验证方法的规则。它可以来自原作观察、实际制作失败或可复现的工程实验；进入默认制作流程前，需要比较候选与基线的具体结果。

## 七个阶段

| 阶段 | 输入 | 产物 | 完成条件 |
| --- | --- | --- | --- |
| 研究 | 原作者作品、真实 UV、模型、材质与明确范围的评价 | 来源身份、原尺寸观察、反例、适用范围 | 观察可复查，事实与推测分开 |
| 实验 | 一个待验证假设、固定输入与旧版基线 | 参数、控制变量、运行记录、结果与失败条件 | 差异可重现，未把多个变量混为一个原因 |
| 规则 | 有证据支撑的观察与实验 | 规则 ID、触发条件、动作、理由、例外、验证方法 | 可执行且能被具体结果证伪 |
| 候选 | 选定规则、工具、资源与目标范围 | 固定文件清单、配置、依赖与差异 | 能确定正在审查的准确内容 |
| 评测 | 候选与基线、固定任务、相同观察条件 | 并排结果、机器检查、人工评价与失败记录 | 技术必过项完成，退步和未执行项明确 |
| 审查 | 具体结果、规则差异、评测记录、拟发布清单 | 与候选及文件身份对应的采用决定 | 规则、工具、素材和发布范围分别明确 |
| 发布 | 已获批准的候选与固定清单 | 独立安装包、版本记录、摘要、远端核验 | 输出自包含，下载内容核对一致 |

操作完成、技术检查通过、美术认可、允许上传与允许发布分别记录。局部认可只覆盖被评价的版本和部位；目录迁移、构建成功或检查器通过不会扩大这个范围。

## 模块如何合作

| 模块 | 负责什么 | 当前入口 |
| --- | --- | --- |
| 研究 | 证据整理、实验设计、候选规则、独立评测 | [`wt-skin-study`](../../src/study/wt-skin-study/) |
| 工程 | 输入身份、原生 UV、通道、导出、工程与交付检查 | [`wt-skin-build`](../../src/build/wt-skin-build/) |
| 风格 | 配色、图形语法、字标、留白和结构关系 | [`src/styles/`](../../src/styles/) |
| 载具配置 | 目标资源、表面、镜像、共享 UV 与绑定约束 | [`profiles/`](../../profiles/) |
| 领域工具 | 可复用计算、检查与图像处理 | [`toolkits/`](../../toolkits/) 及风格包内的领域专用工具 |
| 评测 | 记录契约、证据关联检查与回归 | [`evals/`](../../evals/) |

这些分层服务于源码维护。独立分发时由构建器带齐单包所需的文件，使用者无需为了一个风格包额外安装其他 Skill。飞机与地面工具的适用域仍分别保留；目前的载具配置只有 schema 与合成示例。

## 从一项改进开始

1. 确定要解决的具体问题及不应退步的行为，固定现有版本作为基线。
2. 给来源、输入、规则与运行分配稳定 ID，保存文件摘要和观察条件。
3. 进行单因素实验，保留成功、失败、人工修补与重试记录。
4. 将结论写成有触发条件和例外的规则，按范围放入研究、工程或风格候选。
5. 检查候选的记录与装配，在同输入、同相机、同导出条件下比较。
6. 提交具体图像、规则差异、失败边界和拟发布清单供审查。
7. 仅在批准范围内采用并发布；未采用的结论保留为假设或反例。

普通制作在既有规则与目标条件匹配时直接进行。遇到新风格、新表面、规则失效或明确研究目标时，再开启上述轮次。

## 保留工程能力，逐项验证新规则

现有原生 UV 作画、模型检查、材质处理、分层编辑、包身份校验和明确版本的正反评价继续保留。新的评测流程分别报告技术效果、视觉质量、游戏表现、重复性与迁移能力。

研究用例、调参回归与未见留出在规则提炼前划分。已经观察或用于修复的作品不能再次标记为未见样本；留出答案不装入生产 Skill。新增模块是否提升效果，需由这些实验和人工评价回答。
