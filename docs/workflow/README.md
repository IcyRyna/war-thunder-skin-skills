# Skill 研发流程提案

状态：候选，待维护者审查。本提案描述下一阶段的研发方法；现有安装包、版本线和制作规则仍以各自发布版为准。

目标是让每条制作规则都能回答三个问题：它从哪里来，在哪些条件下成立，怎样验证它比旧方法更好。

## 六个阶段

| 阶段 | 输入 | 必须形成的结果 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 研究 | 原作者作品、真实 UV、模型、材质及已明确范围的评价 | 来源身份、原尺寸观察、反例和适用范围 | 观察可复查，事实与推测分开 |
| 规则 | 可追溯的观察与失败案例 | 带触发条件、动作、理由、例外和验证方法的候选规则 | 规则可执行，且能被具体结果证伪 |
| 配置 | 候选规则、载具表面与风格语言 | 载具配置和风格配置；不混入任务专属素材 | 参数足以说明变化来自哪里 |
| 评测 | 固定任务、旧版基线、候选版和相同输入 | 并排结果、机器检查、人工审美结果和失败记录 | 通过必过项，并说明退步与适用边界 |
| 审查 | 具体图像、候选规则差异、评测证据和拟发布清单 | 与版本、部位、文件哈希绑定的维护者决定 | 明确确认采用哪些规则、工具与素材 |
| 发布 | 已通过审查的候选与固定文件清单 | 独立安装包、版本记录、摘要与验证收据 | 安装包自包含；远端标签和下载附件核对一致 |

操作完成、技术检查通过、美术认可、允许上传、允许发布是不同事实，分别记录。美术认可可以只覆盖局部；规则采用与软件发布需要各自明确范围。

## 从现有系统保留什么

保留可复现的原生 UV 制作、模型和贴图检查、分层编辑工程、包与安装身份校验、已明确版本的正反评价。将工具能力与审美结论分开：脚本能算出覆盖率，不等于构图已经合格。

历史方案不因进入新流程而自动获得认可。被否定的方案保留失败条件；已封存流程仍保持封存。新规则先在固定任务上与现有基线比较，再决定替换范围。

## 职责划分

拟议的 `wt-skin-study` 负责研究、规则与独立评测，`wt-skin-build` 负责输入契约、原生 UV、通道、导出和工程检查，风格包定义视觉关系，载具 profile 映射实际区域与约束。这是职责划分；不要求用户同时安装或手动调用多个 Skill。现有飞机工具不能通过改名直接获得地面载具能力，未统一的领域适配器保持独立且固定版本。

普通制作在已有规则与 profile 适用时直接进行。遇到新风格、新表面、规则失效或明确研究请求，再进入完整研发轮次。

## 创作源码与独立分发

研发端可以维护公共工具内核、载具配置、风格配置和评测集。构建时将需要的内核与参考资料装配进每个 Skill，保持单包安装、单包运行。一个发布包不得要求用户另外安装另一条 Skill，也不得通过机器上的相邻目录寻找依赖。

公共实现复用降低维护成本，独立包让用户按需安装；两者通过确定性装配和文件清单连接。这个结构是待审查的研发建议，尚未改变任何已发布 Skill。
