## 拟议研发分层

| 层 | 责任 | 边界 |
| --- | --- | --- |
| 公共工具内核 | UV、几何、材质、图像与验证工具 | 不依赖某位作者的审美偏好 |
| 载具配置 | 资源身份、表面分区、UV、镜像、结构与绑定 | 不保存任务角色立绘或最终作品 |
| 风格配置 | 配色、图形语法、字标、留白和例外 | 每条规则链接到证据及适用范围 |
| 评测集 | 固定输入、参考基线、反例、指标和人工评价 | 研究用例与留出的迁移用例分开 |
| 包装清单 | 每个 Skill 包的文件、依赖和许可证来源 | 产物可在独立目录内验证 |
| 制作任务 | 本次素材、设计源、预览、交付和用户反馈 | 与可复用源码分离，按当前版本索引定位 |

这些是责任划分，不要求一次性移动旧工程。先建立清晰的入口和映射；只有依赖已查清、迁移计划可复核时才搬运。迁移保留文件原字节和用户评价，历史路径保留可追溯映射。

## 版本与发布

每个 Skill 继续沿用自己的版本线、标签和更新记录；工作区修订号、作品版本、Skill 版本与打包尝试号分别记录。研发目录名不代表已发布，也不决定当前版本。

每个发布包需要：固定输入清单、装配版本、完整输出文件清单、SHA-256、检查结果，以及明确的采用与发布范围。标签指向的源码、Release 附件、版本索引与已安装内容分别核对；不以提交成功代替下载核验。

公共内核若发生变化，只重新装配受到影响的包，并分别记录差异。独立分发包必须带齐自身脚本与必要参考，不链接到其他 Skill。

旧 Release、标签和已被引用的作品版本保留。整理仓库介绍时不改变其作品评价；删除本地冗余文件前，先确认依赖、已登记当前版本与可恢复备份。

## 分阶段采用

1. 审查这组流程提案以及具体证据、规则差异。
2. 用既有作品和固定小用例试运行记录与评测，不发布新 Skill。
3. 对选定规则与工具逐项作出采用决定。
4. 按批准范围装配和发布受影响的独立包。
