# War Thunder 涂装工程

此入口是**开发中的工程 Skill，尚无正式发行版本**。它把已有工程能力与审美规则分开；安装包从同一工具源组装原字节脚本，不意味着脚本的历史默认值已成为通用规则。工具身份见 [工具来源](tool-provenance.json)，能力与依赖边界见 [工具索引](references/tool-index.md)。下列包内路径和命令适用于构建后的独立包。

## 输入与边界

读取当前任务要求、已登记版本和用户评价，确认下列输入：

- 生产 brief：载具和改型、平台、需要修改的范围、必留区域、输出与验收要求。
- 有版本与哈希的 [vehicle profile](references/vehicle-profile.md)：模板、实际贴图资源名、语义区域、遮罩、UV/坐标映射、材质解释及适配器。
- 设计或风格规范：明确引用的规则版本与资产。缺少规范时按当前用户要求完成设计选择；不得从历史工具默认值推断配色、结构保留方式、人物布局或表面质感。
- 本机能力：Python 依赖、编辑器、解码器和游戏验收条件。不能把外部工具的路径写在文档里就算已经集成。

通用工程只决定**如何实现和验证**。风格决定颜色、构图、图文、结构可见程度与材质目标；载具 profile 决定实际文件、坐标、共享区域和通道映射。profile 是供执行者校验、翻译到 CLI 的语义合同，现有脚本**不会自动读取或执行它**。

独立风格包须打包自己的所需工程工具与技术参考，记录工具快照哈希。用户调用独立风格包时使用该包的入口，不依赖本包被自动加载，也不同时加载另一套相互冲突的制作默认。

## 执行

1. **冻结输入。** 核对当前任务、模板、资产与工具快照；将输入复制或只读引用到任务范围。续作保持已接受部分，列出实际待修改项。使用新的 `workbase/vN`、`delivery/vN` 和对应预览路径。
2. **检查资源。** 用 `inspect_skins.py scan --hash --strict` 检查 BLK 和文件，必要时实际解码；核对确切 `from`、wildcard 和目标文件。错误先修，未解码不能声称像素正确。
3. **确认适配。** 读 profile 中的轴向、纹理角色、语义区域和共享 UV。新载具先用方向／编号定位图、模型与所需游戏截图建立证据；不能复制旧机型的坐标。地面载具缺少匹配适配器时停在适配任务，不能用飞机脚本的通过记录声称坦克已支持。
4. **分层制作。** 选择直接 UV、米制矢量或正交投射路径，见 [实际操作](references/technical-workflow.md)。保存源图层、设计 JSON、矢量与使用参数；几何与 UV 保持原契约。样式相关工具仅在明确规则要求时使用，见 [工具索引](references/tool-index.md)。
5. **保护材质。** 未修改通道保持原值；按 profile 处理颜色 alpha、打包材质与法线。先读 [材质边界](references/material-contract.md)。没有通道证据时先完成可独立进行的颜色制作，记录材质缺口，不凭名称猜测、不默认压平法线。
6. **导出并复检。** 从实际编辑源导出，组装到新目录；验证引用、像素往返、通道与源码身份。DDS 独立生成并验证实际 mip，不替代原 TGA 包。按 1:1、整机尺度、相同相机和规定光照检查。
7. **关闭工程问题。** 检查全体规定视图、共享区域、接缝和禁止覆盖区域。保存工程复制后重开，做可逆修改与重导出，保护交付原件。每个失败保留对应范围与复查，不用局部成功撤销其他失败。
8. **交付与评价。** 提供可编辑源、实际包、输入／输出哈希、技术检查、模型／游戏证据及剩余项。文件检查、离线模型、游戏验证、用户风格评价分别记录；`not_run` 和 `unknown` 不计通过。

## 完成条件

只有所需检查有对应证据才标相应阶段通过。不能运行游戏时可交付 `pending_game_validation` 候选，并给出具体截图清单；文件成功生成不等于游戏或风格通过。用户未审查的新规则、工具和作品保持候选状态；进入共享仓库、安装正式 Skill、赋予正式版本或同步正式源前，必须具备用户对具体对象和范围的明确放行。开发源码获准进入仓库，不会自动获得正式发布或作品通过状态。

运行时使用 `python -B`；Windows 管道输出先启用 UTF-8。输出均进入任务目录或测试临时目录，不写回 Skill。最小可运行工程例子见 [合成示例](examples/synthetic/README.md)；它只验证工程链路，不能作为真实载具或任何风格的通过证据。
