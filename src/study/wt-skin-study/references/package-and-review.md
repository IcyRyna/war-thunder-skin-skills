# 候选封装与审查

用于把已经整理的知识编成 Skill，或决定哪些修订可以晋升。发布是独立动作；研究、测试和上传授权按当前用户请求与工作区约定判断。

## 职责与分发

研究方法负责提出与验证知识；通用制作负责资源、编辑、导出和检查；风格负责视觉关系；载具 profile 负责实际 UV、材质与语义映射。职责分开不等于运行时必须同时加载多个 Skill。

独立风格包应包含本次执行所需的通用流程、脚本、参考和可分发资产，安装一个包即可在其声明环境中执行。开发源码可以共享核心；构建时复制受控版本进入独立包，生成文件从共享源码构建，不手改生成副本。

验证时把包复制到临时目录，断开原开发路径，检查所有内部链接、脚本入口、资源和依赖声明。不能依赖本机另一个已安装 Skill、私人研究目录、绝对工作区路径或自动共加载的假设。外部工具属于环境依赖，应明确能力、版本约束和实际不可用时的结果。

## 每次只晋升有依据的内容

进入候选前，为每条改动列出：

- 原规则、候选规则、原因及范围。
- 支持与反对证据，首次结果、返工与回归情况。
- 是否需要新增资产、依赖或 profile 字段。
- 未测条件与可能退化；回退所需的原版本身份。
- 拟纳入生产包的具体文件，哪些研究数据只保留在任务内。

有用的反例可以入包，但只放执行者需要的简明标注和允许分发的材料。个人评价台账、对话原文、机器路径、全部研究截图和历史试验脚本不应为“完整”而塞进生产包。

## 审查对象必须具体

提交实际候选文件、前后规则差异、同条件对比和验证记录。技术检查是技术证据，作品审美认可来自对应评价；二者不能互相替代。

如果工作区要求用户审查后才可正式更新，保留以下独立判断：

1. 作品或实验结果是否被认可，认可到哪些部位与属性。
2. 从结果提炼的规则是否被认可，是否只适用于该机型或分支。
3. 哪些具体文件被允许进入正式源码、安装目录或远端，目标是什么。

授权覆盖当前对象和范围时继续执行，不重复索取。授权尚未覆盖时，先完成可审查的本地候选；提交实际差异后再请求缺少的批准。不能通过候选分支、私密备份或 Draft Release 绕过明确的上传门槛。

## 检查与声明

| 完成事实 | 应有证据 |
| --- | --- |
| 文件已编写 | 实际文件与清单 |
| 包结构通过 | 元数据、内部路径、依赖及未完成占位检查结果 |
| 指定任务试跑通过 | 独立上下文的真实输入、执行记录、全部输出 |
| 指定游戏检查通过 | 对应输出版本的真实游戏记录 |
| 指定重复/迁移范围通过 | 冻结试验及全部结果，含失败和人工介入 |
| 用户审查通过 | 明确版本、范围、评价来源 |
| 正式发布完成 | 已授权目标、实际远端或安装结果、文件身份核验 |

这些事实逐项记录，不用单一“完成”代替。结构检查过的包可以作为下一轮候选；尚未完成行为验证时不能宣称更稳定或优于旧版。
