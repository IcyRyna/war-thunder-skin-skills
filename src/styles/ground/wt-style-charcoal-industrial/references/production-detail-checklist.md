# 整车制作细查：从真实承载面到游戏结果

本页接在[13项部位默认](part-layout-defaults.md)之后使用，解决已经决定“做什么”以后，如何把它完整地做在目标车上。
每一步都针对本次输入、变更部件与交付状态；不要求重做未变化的整车、不自动生成七视图，也不把某次单车选择提升成全车系规则。
字段入口见[候选流程](candidate-workflow.md)；`vehicle_review --stage final`经`final_review.validate_final`实际调用`production_checks.py`的观察与通道修复检查。
历史记录中的具体数值、朝向、版式和用户认可只属于当时车辆；当前用户对本车的明确要求优先。

## 0. 先完成装饰与原皮细节设计

按[部位装饰与材质配方](decoration-and-material-recipes.md)建立大灰区/主图、部位副装饰和原生近景细节三个尺度。主图完成后逐项回看机枪、观瞄、舱盖、附件箱、侧裙后段与车尾小件；这些不能只套主体同一种灰。按[原皮细节复用](native-skin-detail-reuse.md)在底漆前识别有效小标记和结构，避免把它们当污渍清掉。

## 1. 建立能实际追踪的输入链

**实际输入。** 使用目标型号的模型、材质绑定、原生C/N/AO、BLK和本次实际附件；引用已有资源时核对文件与哈希。
先辨认单位配置名、模型资源名与纹理名的关系，不能因为名字相似就假定属于同一变体。
读取纹理尺寸、通道、压缩格式和mip数；区分原生高分辨率条目与低分辨率条目，不用放大低清图冒充补全细节。
保存本次修改前的规范像素基线；基线已经做过固定漆面Alpha处理时，写明该处理及其作用域。
同一个编辑器文档、UV窗口、模型材质槽与导出纹理必须能通过资源ID相互对应。

**具体决定。** 每张使用资源至少说明下列关系，放在本车输入记录或现有绑定报告内，不另外维护中央登记。

| 内容 | 实际记录 | 不通过时处理 |
|---|---|---|
| C | 尺寸、RGB颜色空间、Alpha用途、固定漆面/裁切/光学使用者 | 先拆使用者与保护区，不能全图套Alpha255 |
| N | 尺寸、R/G/B/A物理意义、采样网格、所属shader | 未确认语义先核实，不能只凭`_n`后缀写通道 |
| AO | 实际资源、通道、保持或限定修复范围 | 没有独立AO时记录缺失，不生成白图凑数量 |
| 绑定 | 材质槽、模型节点、全部共享使用者、运行BLK映射 | 追踪漏掉的使用者；不能以“主车体正常”代替 |
| 基线 | 修改前像素、原生来源、已发生的前处理及哈希 | 找回真实输入或重建明确基线，不能把最终图当before |

**观察方法。** Blender先选真实部件，再选对应材质槽与图像；从UV反选实际面，确认前后、左右、内外和隐藏共享者。
脚本读取字节和绑定；模型检查确认这些字节确实指向所说的部件。两者不能互相替代。
输入缺失只阻止依赖该输入的阶段；已明确的其他部件可以继续，但缺失范围不能写成已完成。

## 2. 用“方向×状态”检查真实可见面

**先定交付状态。** 明确网布、外挂、附加装甲及其他可选部件的当前组合，并说明炮塔方向、炮管姿态等实际观察条件。
只增加本次修改会受影响、且目标模型或游戏实际支持的其他状态；不枚举与当前作品无关的所有组合。
例如炮根下方新涂层可能随炮管抬起暴露，才需要增加对应姿态；不能为填表臆造开舱动画或附件配置。

`observation_matrix.states`每项使用以下字段：

- `id`：本车唯一状态ID；`configuration`：真实附件与运动配置，能据此复现观察。
- `status`：`checked`、`not_checked`或`unsupported`；不要用一个笼统“已检查附件”覆盖未看状态。
- `affected_coverage`：该状态影响的现有coverage ID；引用必须指向本车实际范围。
- `checked`提供`evidence`；其他状态提供具体`reason`，说明缺模型、缺状态支持或尚未游戏核验。
- `delivery_state`指向实际交付的状态，且该状态必须已观察；这不自动说明游戏动态效果已通过。

**交付状态逐方向检查。** `views`恰好记录以下六个方向，每项`state_id`都等于`delivery_state`。

| direction | 实际要找的表面和问题 |
|---|---|
| `front` | 前向装甲、首下、挡泥板前面、炮塔前角；文字被拖具/履带遮挡、前向面误铺图案 |
| `rear` | 尾部钢面、警示承载板、灯组与排气相邻面；旧底框、左右完成度和后半段漏面 |
| `left` | 左侧完整侧裙、装甲、附件和铭牌；字向、把手遮挡、前后密度、材质连续性 |
| `right` | 右侧独立检查，不把左侧通过直接复制；共享镜像、设备差异、残留浅底与板面边缘 |
| `top` | 顶板、设备壳体、盖板与图组；从真实可见上方观察，不把底面投影误当顶面 |
| `lower_visible` | 裙甲下沿、可见内侧、炮根下侧、外挂盒背沿、折边；根据实际视角确认遗漏 |

每项填写`status=checked/not_visible`、`coverage_ids`、具体`observation`和冻结的`evidence`。
`not_visible`只表示该交付状态下相应表面确实不可见，仍需证据；不是省略一个方向的捷径。
证据可以复用本次有效局部图或具名检查报告；不得只给空白图、旧版本图或“看过了”一句话。
六方向不等于六张导出图。已有交互预览可连续查看，记录实际场景、资源身份、视角与观察结果。
其他状态的方向观察写在其`states[].evidence`中；当前`views`结构只接受交付状态，不在其中重复同方向。

**发现遗漏后。** 回到原生面组，补全该部件应涂的面；若该面本来应保留，则调整分类与图层范围。
不要用UV侵蚀消掉窄边，也不要把小折面静默标为“不重要”；保护邻件需要追踪共享者后作明确决定。
临时隐藏遮挡件可以帮助选面；完成后恢复真实附件，再检查文字、色标、图案是否仍可见。
本项机器能确认六方向、状态、ID和证据完整，不能从这些字段推导相机真的看到了目标面。

## 3. 左右分别排版，再检查整车呼应

**实际输入。** 左右各自的真实承载面、尺寸、UV方向、共享者、设备遮挡和本车文字内容。
先测每侧可用板宽与板缝，再确定身份图组、装备图组与微色标的位置；不要先机械镜像完成图。
两侧可以位置不同、行数不同、警示条数不同，但主次关系、蜂窝尺度与材质角色应有设计上的联系。

`observation_matrix.paired_surfaces`为需成对比较的区域建立记录；不是要求把全车所有面强配成左右对。
每项`left`和`right`分别包含`coverage_id`、`local_axis`、`reading_direction`、`occlusion`与`evidence`。
`comparison`写实际结论：哪些颜色/尺度/材质相同，哪些因设备与板形不同而调整；不能只写“对称”。
`local_axis`描述原生载具坐标或已冻结局部轴，`reading_direction`描述从实际观看方向读字的顺序。
UV窗口中的左到右不保证游戏里左到右；顶部手性也不能照搬侧板。以真实模型检查正字与字顶朝向。

**共享冲突。** 同一像素被镜像使用且文字方向冲突时，先找独立原生UV承载面，或改用无方向图形。
不能在同一区域重复写一次期待左右独立；普通涂装路线不修改模型UV，改UV另需本次明确授权。
同一无字图案允许重复使用时仍检查物理尺度和方向；不能只因无字就忽略折面、拉伸与遮挡。

**色差诊断。** 比较语义相同的实际漆面，排除图案、孔口、五金及原生保留区，再看C与N/AO。
采用同光照、可比较相机条件；先查整片底色和旧底板，再查材质、结构法线、AO与环境反射。
C一致但高光不同，不能直接把一侧调黑；C整片偏浅，也不能只擦旧条纹的轮廓。
左右单独布局和成对观感由实际观察确认；机器只能检查对应范围、参数和声明的一致性。

## 4. 动态网布与基础迷彩图的专门分支

**开工即决定。** `observation_matrix.dynamic_net.state`只能为`absent`、`native_preserved`或`target_pattern`。
每种选择都提供`reason`和`evidence`；模型里没有网布不能只凭文件名猜，保留网布也要说明实际资源和状态。
先核实目标shader怎样使用基础迷彩、原生网布C/N/AO与裁切Alpha，再选择该车支持的替换路线。
Barracuda的历史案例是基础迷彩图继承，不表示所有网布或shader都支持同一种替换。

**制作目标周期图案时。** 使用本车对应尺度与方向，接缝处检查图形、颜色和实际周期连续性。
在目标网布上看图案分布，不能把一张普通钢板上的网孔照片当作网布几何或动态效果。
基础迷彩的全部共享使用者都要追踪：钢面、运行履带及其他材料不应意外获得新网布纹样。
已经固定漆面的钢件及需要保留原生外观的共享资源，按本车已核实绑定明确隔离。
网布原生裁切Alpha与N/AO各按职责保留；擦除C.Alpha不等于已成功删除游戏网布。

`target_pattern`须逐项完成并记录`periodic_edges`、`all_shared_users`、`cutout_alpha`和`native_materials`。
这些字段为true必须有对应实际工作；机器不会从true推导周期纹样或动态材质视觉正确。
`game_status=checked/not_run`独立填写；写`checked`必须提供`game_evidence`，说明实际车型、附件和加载版本。
离线静态变形不支持时保留限制；隐藏网布检查钢面后，不能宣称最终游戏已经去网或所有状态通过。
出现共享污染先修绑定和使用者范围，再改图案；出现断周期先修图案接缝，再判断是否需调整物理尺度。
动态图案的运动、拉伸、基础迷彩继承与游戏显示只由对应游戏观察确认。

## 5. 不同C/N/AO网格：同一物理位置，不等于相同像素坐标

**实际输入。** 各纹理的原始尺寸、UV、通道语义、承载面物理尺寸及每张图的明确基线。
为每个新颗粒/细线/法线图层写明：物理尺度、目标C密度、目标N密度、目标mip和实际覆盖范围。
在本车记录一份网格转换说明，引用生成/重采样的输入、参数、输出与哈希；不要把它假装成工具已自动推断的事实。
例如C为8192×4096、N为4096×2048时，同一UV覆盖的C/N遮罩须分别栅格化或显式映射。
不能将C遮罩直接当作N遮罩；也不能把N上一个像素视作C上一个像素而改变实际颗粒尺寸。
材质`final_samples[].uv_mapping`使用`mode=same_native_uv/independent_uv`，并填写`color_texture`及冻结的`evidence`。
`same_native_uv`指同一原生UV关系，不要求C/N尺寸相同；工具会用N网格上的实际mask重查覆盖。
`independent_uv`另提供`normal_coverage`的文件/哈希，明确N自己的真实面与UV；不能只填“独立”便免查。

**生成与变换顺序。** 从同一高度场得到颜色细节、粗糙度和法线，再按同一UV映射生成各通道目标网格。
禁止分别用不同种子生成C颗粒和N颗粒；画布尺寸一致也不保证两者同源或位置一致。
数据通道按标量/向量语义重采样，N.A作为法线Y处理，不能进行普通RGBA透明度合成。
法线的旋转/镜像要同步变换切线向量；法线的方向约定与目标shader不一致时，先确认转换再合成。
镜像纹理的处理还要与实际UV切线手性对应，不能只看到图片左右反转便盲目统一翻转某通道。
需要合并微法线时使用已声明细节覆盖与RNM流程；保留原生接缝、卡箍、焊缝等结构朝向。

**窄面处理。** 检查每个小折边、细框和小保护面的目标网格采样，不以面积占比高掩盖整条细边消失。
低分辨率网格若无法独立表达目标与保护面，先改承载布局/尺度，或在预算与来源允许下选择合适分辨率。
不要以扩张到无关UV岛补漏，也不要以侵蚀整层回避冲突；明确记录目标分辨率无法表达的部分。
只上采样不能恢复原本不存在的细节。新生成颗粒可按真实采样重新生成，但不得宣称恢复了原生信息。

**不通过时修改。** 颗粒太细先调整物理粒度或生成分辨率；C/N错位先修UV映射，不靠模糊遮住。
法线凸凹方向错先查方向约定和变换；保护区受影响先修独立遮罩与网格转换，再重新导出。
机器可检查尺寸、哈希、同源记录、变更范围和目标样本；颗粒是否合适、微高光是否自然仍看最终模型。

## 6. 撤旧图与修复表面：逐通道判断，不做全图复位

**先辨认残留。** 在相同光照下看旧字晕/底框/条纹，再分别查看C、R、B、G/A、AO，确认原因在哪一层。
选取真实受影响面和邻近同材质面作比较；不得按亮度把正常暗漆误当孔洞，或按颜色挑“合格样本”。
一次只更改已判明的通道；需要试验时保留真实前后输入和结果，阴性结果也要记录。

每个`channel_repairs`记录对应一次有边界的旧效果修复，提供`reason`、诊断`evidence`及完整`decisions`。
`decisions`恰好包括`C_RGB`、`C_A`、`N_R`、`N_B`、`N_GA`和`AO`六项，不能只写“清理材质”。

| 项目 | 先检查什么 | 常用处理与保护边界 |
|---|---|---|
| `C_RGB` | 旧文字/底框颜色、整片偏浅、低频污色 | 回退真实旧效果或限定重建底漆，保留本次有效图案 |
| `C_A` | 固定漆面覆盖、镜片透明、枪体/网布裁切 | 按已核实shader与像素用途保留或回退，不能跟RGB一起刷白 |
| `N_R` | 条纹粗糙度印迹、异常镜面宽度 | 只恢复受影响区目标粗糙度，不把全车变成同一光泽 |
| `N_B` | 旧抛光/金属区、钢面与聚合物串材质 | 按该面实际材料恢复或新设，不能复制别车固定数值 |
| `N_GA` | 旧防滑边框、粗斑凹凸、法线变换错误 | 明确修复允许区；接缝、螺栓、卡箍和合理微表面另保护 |
| `AO` | 旧效果是否真的写入AO、结构阴影是否原生 | 默认保留；仅在证据与本次范围允许时作限定修复 |

**动作的实际含义。** 每个决定选择`preserve`、`restore`、`modify`或`absent`。

- `preserve`：该通道全图与修改前快照一致，不只是遮罩外一致；适用于判明无须处理的通道。
- `restore`：遮罩内等于明确的`restore_from`来源，遮罩外等于本轮`before`；不能把任意相邻颜色称为原样恢复。
- `modify`：限定范围内采用声明的新方法，填写`method`；重建/去污/平滑结果如实称修改，不伪称原像素未变。
- `absent`：实际不存在该资源，提供`reason`与`evidence`；Alpha恒255不等于Alpha不存在，语义未知也不是absent。

前三种动作都提供`before`、`after`和`mask`的文件/哈希；mask是该通道网格的独立L8二值范围。
`before`为本轮修复前的真实快照；`restore_from`是旧效果加入前或明确冻结的目标恢复来源，两者职责不同。
`before/after/restore_from`尺寸必须一致；尺寸不同先完成显式网格映射，保留映射前来源与方法，不能偷偷缩放。
`N_GA`共同检查G与A；`AO`按规范RGBA读入的全部通道检查，不能把单通道数据误用显示透明度解码。
修复审计检查规范像素的精确范围；最终有损DDS压缩误差还需在导出阶段按实际通道审计，不能由此忽略。
实际修改AO时，该记录的`runtime_texture_id`必须对应运行清单中的AO ID，AO决定的before/after必须分别绑定其baseline/canonical哈希。

**检查结果。** 遮罩外任一受检查通道变化即失败；preserve出现变化即失败；restore与来源不符即失败。
modify仅证明变化受限，不能证明新方法在视觉上修好了问题；需重新查看真实模型及相关材质角度。
不要反复在已平滑过的N上乘强度或去噪；从冻结输入应用一次明确参数，保留结构与微表面职责。
AO保留、C修复或G/A修改各自如实记录；不能将一次C导致的发白推广成所有发白都只需修C。

## 7. 文字、蜂窝与颗粒：按用途分配近中远尺度

**先定义看什么。** 关键车型字标、功能警示、蜂窝主带、微色标和纯微纹理具有不同阅读任务。
在本车设计记录中写明期望观察距离/模型占屏大小、相机条件与关键特征；不使用跨车型固定米数作为审美门槛。
远中近应能复现，不能每次换一个大小却都称“常用距离”；已有视角可复用，无需重新导出整套图。

| 距离 | 要读到的内容 | 典型返工 |
|---|---|---|
| 近 | 字形、行距、留边、格缝、法线细节和保护边缘 | 修字距/线宽/UV采样/局部变换，清除字晕与源图残片 |
| 中 | 身份与警示的层级、蜂窝尺度、色标节奏、材质区分 | 重排承载图组，改变尺度或减小细节密度，不只锐化整图 |
| 远 | A/B/C主次、大几何、侧带和焦点关系 | 调整大色区与疏密，不靠加满细白线补救 |

当前细节预算以[原生接口](native-profile.md)与统一规则的实际入口为准；历史8px字高底线不是当前12px工程预算的替代。
按最终有效字形/笔画计算，不按透明PNG画布尺寸计算；倾斜投影使用局部最小缩放，不能只检查中心。
这些数值只拦截明显不足，不意味着达到像素门槛就自然、清楚或适合该车。
未知微字不能臆造补全：保留为不可读微纹理、重做明确获准内容或明确省略。

**蜂窝检查。** 主带细密、局部焦点较大，实际板面与禁绘面分别处理；观察斜视时格缝是否粘连、闪烁或形成杂纹。
先判断问题来自图案尺度、细线预算、透视拉伸还是mip滤波，再调整相应项；不要把每车都改成同样六边形尺寸。
**颗粒检查。** 原始目标级应有可采样细节，远处mip允许自然消退；不要求1×1 mip仍显示颗粒。
把防滑图案的结构边界与微粒度分开，允许颗粒变平但不能由缩小产生明显错误边框。
阅读正确性、疏密及材质自然程度属于实际视觉判断；机器只计算声明输入上的像素与范围。

## 8. 最终DDS、mip与LOD：三种通过分别记录

**第一种：文件与解码通过。** 检查格式、尺寸、全部mip数量/大小/可解码性、实际运行文件身份及BLK映射。
不能只解码顶级mip后便把全部mip写为通过；也不能删除mip凑包体预算。
**第二种：通道与边界通过。** 每级按C/裁切/N/AO实际语义核查Alpha、法线数据、保护边缘和压缩误差。
当前`runtime_validation`实际读取每份交付DDS的所有mip，与编码前`canonical`按声明语义生成的mip逐级比较。
每份DDS声明`encoding.mode=exact/bounded`；bounded提供逐通道`max_abs/max_mean`、法线角误差上限与目标证据。
上限是实测合同，不是默认把工具允许的最大值全部填满；C/N/AO语义、DDS颜色空间标签与模型槽还要一致。
贴花滤波与数据N滤波分别处理；不得把N.A交给透明度预乘流程，或把预览图吸色当解码数据。
**第三种：模型观察通过。** 绑定本次最终DDS，在对应距离、斜视与转光时检查渗色、闪烁、格缝及细边。
第三种不能被第一种替代，布尔字段`all_mips_rebound`本身也不证明每一级视觉正确。

重点检查贴近玻璃、孔洞、百叶与网布裁切的颜色，窄框条、图岛边距、共享小面和强色警示边缘。
顶级零越界只说明当前网格样本，低级mip及过滤仍可能把邻域混入；先修图案边距、覆盖与导出过程。
不要为了消除渗色把真实小面裁没；在实际资源和包体允许范围内选择可表达该边界的格式与尺寸。
记录有损变化的真实误差；如果保护约束无法满足，解决格式/布局问题，不把全图精确保护改成宽容差口号。

`observation_matrix.available_lods`记录实际获得的原生LOD及其范围：`id`、`status`、`observation`，已核验者提供`evidence`。
`status=checked/not_obtained/not_supported`；不要凭空填LOD数量，也不要把只获得LOD0写成全部LOD通过。
检查所得LOD的材质槽、UV对应、共享与贴图绑定；切换时若使用不同资源，纳入本车实际运行清单。
没有获得的LOD明确未核验；需要实际游戏看模型切换效果时，以对应游戏记录补充，不用离线同一模型重复截图替代。

## 9. 工具分工与返工闭环

| 顺序 | 负责的工具/实际动作 | 形成的结果；未通过时回到哪里 |
|---|---|---|
| 1 | 脚本读取资源、尺寸、shader线索、通道及绑定 | 冻结本车输入；缺资源或语义不明先补该输入 |
| 2 | Blender核对真实部件、UV、共享、状态与承载面 | 本车面组/轴/尺寸；错面、漏面、共享冲突在此解决 |
| 3 | 制作者安排13项布局、方向状态、两侧关系和像素预算 | 本车设计决定；超载承载面时重排，不先强贴 |
| 4 | PS/Composa实际分层组装/编辑、保存、导出与副本重开 | 可编辑工程及可追踪C来源；导出不符先修图层/通道路径 |
| 5 | 精确脚本处理遮罩、R/B、法线、修复审计和网格映射 | 规范像素与限定变更；范围错误回到面组或通道基线 |
| 6 | 脚本生成DDS/mip和BLK，逐级读回并检查包体 | 当前运行文件；格式/通道/压缩失败就在导出阶段修正 |
| 7 | Blender与既有预览绑定最终DDS，按状态与距离观察 | 实际文件的局部/整车结论；视觉缺陷回到对应布局或材质 |
| 8 | 游戏核实选中名称、安装目录、文件版本、shader与动态显示 | 真实游戏范围与反馈；未运行则明确保留未验证项 |

最终C来源必须唯一声明：使用哪一次真实编辑器导出，后续精确脚本又改了哪些像素/通道。
若编辑器结果只作对照，应说明最终规范合成来源与两者比较；不能把脚本平图打开一次称为真实分层制作。
N/AO的数据处理可由脚本承担，不能因必须使用编辑器而把数据Alpha当普通透明图层处理。
重开工程使用副本；只收尾本批自有文档，保存失败保留检查点与错误，不强关用户文档。

**局部修订后的最低回查。** 颜色变化重查对应色区、保护区与左右比较；图形变化重查承载、字向、像素预算及mip。
材质变化重查R/B/G/A、同光照及转光；附件/作用域变化重查全部受影响共享者和观察状态。
任何最终文件变化均重查本次导出身份与最终绑定；未受影响的有效证据可复用，不重复制造整车展示图。
发布与用户认可保持独立。本页的技术与离线流程不授予上传、安装候选Skill、修改模型UV或生成七视图的权限。

在Skill根目录执行实际检查，报告输出路径须为本轮新文件：

```text
python -B scripts/vehicle_review.py vehicle-review.json --stage final --out final-check.json
python -B scripts/delivery_validate.py --manifest vehicle-review.json --zip final-game.zip --out delivery-check.json
```

`delivery_validate`先重新执行final，再核对ZIP成员集合、包内路径、逐成员哈希与已审核运行文件完全对应，并执行包体预算。
它能拒绝多文件、缺文件、错路径、旧DDS或错BLK；不能证明游戏当前选择了该目录，也不能从ZIP通过推导美术认可。

## 10. 哪些必须留给本车决定

圆盖是否连续炭灰、首上是否蜂窝、是否大V、前挡泥板是否留白、是否有贴纸边框，都由实际构成和用户要求决定。
警示组数量/朝向/尺寸、左右位置/条数、蜂窝物理尺度、网布周期及全部R/B值不跨车固定。
某次接受共享槽底联动，只适用于当时核对的使用者；新车必须重新追踪，不沿用“历史上接受过”。
通用默认是处理完整的物理角色、明确保护范围、让整车主次与材质成立；不能把单车返工写成永久禁令。

## 11. 记录通过所能证明的边界

`validate_observations`检查状态/方向结构、交付状态、引用、配对字段、网布选择与LOD记录，不执行相机观察。
`audit_channel_repair`检查实际规范像素、精确范围、保留不变及恢复来源，不自动诊断旧残影原因。
`runtime_validation`已检查全部mip的编码误差与原生BLK槽映射；实际过滤观感、游戏shader与动态结果仍由对应观察负责。
结构化记录中的证据应由执行者实际核对内容；文件存在和哈希吻合不能证明画面正确或观察完整。
文字自然、左右平衡、蜂窝疏密、材质高光与整体风格由真实模型视觉判断；游戏shader和动态效果由相应游戏观察判断。
技术、离线视觉、游戏验证、用户认可分别记录，不从其中任意一项自动推导其他项。


## rc2实际回归的三个补强

顶部预检从实际墨迹、支撑面和独立物理边界计算，而非自填尺寸/余边；单平面矩形不能处理10式沟槽上的真实有效墨迹。当前源图、frame、模型、几何与遮挡计数必须绑定同一版。主图组尺度与实际可见性使用本车明确目标，例外有具体依据，不能把readable=true当观察本身。

删除图案时，intent=remove_graphic还须逐通道证明清理目标。reference指可信pre-effect或明确重建目标，constant指本车对应材料目标，not_written依真实旧效果写入谱系。当前快照可以作为受控故障注入参考，但不能因此称美术干净。

已知设备的casing/working_face/mechanism必须实际拆组；旧4k mask不能直接套模型已改UV的双页8k图。源包、模型依赖与活动BLK先核对，再解释颜色或覆盖差异。
